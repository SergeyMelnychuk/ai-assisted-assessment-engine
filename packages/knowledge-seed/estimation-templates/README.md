# Estimation templates

This folder holds **sample estimation workbooks** that ship with the
engine. Customers can upload their own templates per-engagement; the
files here are the defaults the seeder loads on a fresh install.

## What lives here

- `wbs-and-estimates-v1.5.xlsx` — full Work Breakdown Structure +
  per-role estimation workbook. 19 sheets covering: solution-context
  sizing, WBS, BA / Arch / QA / DevOps / PM / UI-UX per-role
  estimation, buffers + non-dev activities, rates, internal cost &
  profitability, headcount + monthly cost roll-out, fixed costs,
  maintenance, and a WBS comparison sheet. Uses named ranges
  (`EnumRoles`, `EnumSeniorities`, `EnumPhase`, `EnumLocations`,
  `EnumYesNo`, `EnumInclude`) to drive validation in the input
  cells.

## How the engine uses these

The Team & Estimate step (Phase 4 workflow) reads a template and
fills it in based on:

- The role catalog (`packages/knowledge-seed/role-catalog/`)
- The active rate card (`packages/knowledge-seed/rate-cards/` or a
  per-engagement override)
- Findings + scoring (analysis output)
- The agent's role proposal (`runEstimation` service)

The filled workbook is exported as a deliverable. See
`docs/guides/templates.md` for the user-facing flow and
`docs/architecture/decisions/0018-template-binding.md` for the
binding model that maps engine outputs to template cells.

## Adding a new template

1. Drop the `.xlsx` (or `.docx` for narrative deliverables, `.pptx`
   for decks) here.
2. Add a JSON sidecar (`<filename>.binding.json`) that maps engine
   outputs to named ranges or `A1:B5`-style cell refs (see the
   binding-spec document).
3. Re-run the seeder (`pnpm db:seed`) to register it as a default.

For customer-supplied templates the same binding sidecar is
generated by the agent on first upload (with the customer's
review/approval).

## Binding sidecar convention

Every workbook or document in this folder ships with a sibling
binding file:

- `wbs-and-estimates-v1.5.xlsx`
- `wbs-and-estimates-v1.5.binding.json`

The JSON file matches the `BindingDocument` schema in
`apps/web/src/server/services/template/binding.ts` exactly. Its
shape is:

```json
{
  "version": 1,
  "templateKind": "ESTIMATION",
  "entries": [
    {
      "field": "totals.costLow",
      "target": { "kind": "xlsx.namedRange", "name": "EstTotalLow" },
      "format": "currency"
    },
    {
      "field": "roles[*].roleName",
      "target": {
        "kind": "xlsx.tableRow",
        "sheet": "WBS",
        "startCell": "B8",
        "column": "B"
      },
      "groupKey": "roles"
    }
  ]
}
```

The full list of engine output fields you can bind, and the full set
of supported target kinds, lives in `binding.ts`. That file is the
source of truth — the schema validator running at install time and
on every binding save reads from the same module, so anything not
listed there will be rejected.

> **Note:** `roles[*].hoursLow|hoursHigh|costLow|costHigh` are
> currently emitted as `0` by the engine; the per-role distribution
> work is tracked as a follow-up in ADR-0018. Seed templates that
> bind those fields will write zeros until that lands. Totals and
> aggregates are unaffected.

### How the seeder loads sidecars

On `pnpm db:seed` the seeder walks this folder and, for each
workbook with a sibling `.binding.json`:

1. Uploads the binary to MinIO under `templates/<id>.<ext>`.
2. Inserts a `Template` row with `engagementId = null` (workspace
   default) and `bindingJson` set to the parsed sidecar.
3. Stamps the row directly as **APPROVED** — seed templates skip
   the `PROPOSED → APPROVED` review flow because the binding has
   already been authored by the engineering team and committed to
   git alongside the workbook.
4. Records a `TEMPLATE_UPLOADED` + `TEMPLATE_APPROVED` audit pair
   attributed to the seed user.

Re-running the seeder is idempotent: an existing row with the same
`(name, kind, version, engagementId=null)` is left alone. To ship a
new version, bump the `version` string in the seed config and check
in a new pair of files — the next seed run inserts the new row and
auto-deprecates the old approved one (same `(name, kind, scope)`
rule as for customer uploads).

### Lifecycle, in short

| Stage | Status | How it gets there |
| --- | --- | --- |
| Customer-uploaded | `PROPOSED` → `APPROVED` | AI proposer drafts binding, human approves (Retry available on proposer failure) |
| Seed templates | `APPROVED` from the start | Sidecar JSON committed alongside the file |
| Superseded | `DEPRECATED` | New approved version of the same `(name, kind, scope)` |
| Hidden | `archivedAt` set | Manual archive; required before delete |
| Removed | row deleted | Manual delete on archived rows only |

See `docs/guides/templates.md` for the user-facing flow and
`docs/architecture/decisions/0018-template-binding.md` for the
design rationale.
